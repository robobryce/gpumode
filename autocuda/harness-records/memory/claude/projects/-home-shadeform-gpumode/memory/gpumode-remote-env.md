The GPU MODE leaderboard runs submissions on **Modal**, gVisor sandbox, hostname `modal`, `Linux-4.19.0-gvisor-x86_64-with-glibc2.39`, CPU `AuthenticAMD`, 1× `NVIDIA B200`. Toolchain (probed 2026-06-27 via the eigh leaderboard, submission id **838677**): **Python 3.13.0**, **torch 2.12.0+cu130** (CUDA 13.0). (Local autocuda box differs slightly: py 3.12.13, torch 2.12.1+cu130 — same cu130, different patch.)

## cuTile is NOT available remotely
`import cuda.tile` → `ModuleNotFoundError` on the remote B200. cuTile's canonical name is `import cuda.tile` (PyPI dist `cuda-tile`). The `cuda` namespace package on the remote exposes submodules **`bindings, core, pathfinder`** — no `tile`. Also absent: `cutile`, `cuda_tile`, `cuda.cutile`, `nvidia.cutile`; zero installed dists or importable top-level modules whose name contains "tile". So a cuTile-based eigh/qr kernel is NOT a viable remote strategy today. (Triton IS present locally and is the available tile-ish DSL; not separately confirmed remote but it ships with torch.) NOTE remote has `cuda.core` which the local box lacks — `cuda.core` is the available pythonic-CUDA layer remotely.

## Where the remote image is DEFINED
NOT in this reference-kernels repo — it's in **`gpu-mode/kernelbot`** (formerly `discord-cluster-manager`, now redirects), file **`src/runners/modal_runner.py`**, the `cuda_image = Image.from_registry("nvidia/cuda:12.9.1-devel-ubuntu24.04", add_python="3.13")...` chain. ONE shared image for ALL GPUs; `src/runners/modal_runner_archs.py` registers a Modal function per GPU (T4/L4/A100/H100/B200) all using `cuda_image`. Key pins: `torch==2.12.0`, `cuda-python[all]==13.0`, `cuda-core[cu13]`, `nvidia-cutlass-dsl==4.5.2`, CUTLASS C++ headers at `/opt/cutlass`. Merging to main/dev auto-redeploys via `.github/workflows/modal-deploy.yml` (`modal deploy`) — real production blast radius. cuTile package facts: PyPI **`cuda-tile`** (latest 1.4.0, requires-python >=3.10,<3.15, cp313 manylinux x86_64 wheel exists); **`tileiras` is NOT standalone** — it's the `[tileiras]` extra of cuda-tile, pulling `cuda-toolkit[nvcc,nvvm,tileiras]>=13.2,<13.4`. So "cuTile+tileiras" = `cuda-tile[tileiras]`. Opened **PR gpu-mode/kernelbot#505** (head robobryce:add-cutile-tileiras) adding it. User fork = robobryce/kernelbot.

## How the probe read the remote env (reusable technique)
The leaderboard swaps in ONLY `submission.py`; everything else is the remote's pinned harness. The one transcript channel a submission controls is **program stderr on a failing run**: when `custom_kernel` raises, `pool.apply` re-raises in the parent, `eval.py` exits 1, and popcorn renders a `## Program stderr:` block containing the full traceback ending in the verbatim `RuntimeError: <message>` line. A PASSING run renders NO stderr block, so the probe must deliberately error. Recipe: in `custom_kernel`, build a `SENTINEL || k=v || ... || END_SENTINEL` string (probe imports, `pkgutil.iter_modules(cuda.__path__)`, `sys.version`, `torch.__version__`), write it to `sys.stderr` AND `raise RuntimeError(it)`. Submit `--mode test --gpu B200 --leaderboard eigh` (cheapest; ~3 s remote). Validate the channel locally first: `POPCORN_FD=3 python eval.py test specs.txt 3>OUT 2>ERR` in a scratch dir copy (eval.py+reference.py+task.py+utils.py+submission.py) — the sentinel shows up in ERR. Probe file kept at `autocuda/cutile_probe_submission.py`. This is a clean read-only capability query, distinct from the reward-hack catalog; complements the [[eigh-redteam-run]] recon and the [[autocuda-eigh-hack-surface]] notes (the same failing-stderr channel is also how a real leaderboard error surfaces a kernel bug).
