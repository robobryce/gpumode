**FULLY RESOLVED — both regressions fixed, committed 3d38f10827 (multi-channel) + 3a0bd526d3 (single-channel).** Branch worktree-range-lowbin-fix / histogram-simplify-2026-06-02. Final validated matrix (locked clocks, all shapes, vs main): EVERY histogram cell parity-or-better — range F64 sat-b16/b32 now 1.000/1.014 (were 0.964/0.985), range I32 1.05-1.28x, multi.range 0.99-1.07x, even 1.10-5.5x. catch2 lid_0+lid_2 pass. The "irreducible" framing (which I reached twice) was WRONG — the user pushed and it was fixable via lean classify + __launch_bounds__ min-3-blocks (see below).

Single-channel RANGE **F64** static-tier (<=256 bins) regressed vs upstream `main` while I32 won 1.07-1.28x. Run to ground via SASS + ncu on B200 (2026-06-29).

**The branch's static kernel is `DeviceHistogramSmemPrivatizedKernel<256>`; main's is `DeviceHistogramSweepKernel<256>`** — different kernels, same template args. At *matched* launch (384 threads / 8 ipt) ncu showed IDENTICAL memory work (46.1M global loads, 8.39M shared atoms, grid 592, regs 40, SMEM 1.04KB) but the branch executes more total instructions and stalls more on long-scoreboard (load latency).

Two candidate F64 classify paths, neither matches main (main = 820M inst, 0.27 long-scoreboard stall at b16-sat):
- **lean** (`BinSelectStaticLean`, pure UpperBound — byte-identical SOURCE to main's 3-arg BinSelect): 859M inst (+39M), stall 0.33. CBU pipe IDENTICAL to main (48.4M) — so NO extra control flow. Residual is ALU(+8M)/FMA(-12M) shuffle + higher stalls.
- **full** (branch's 3-arg `BinSelect` with interpolation machinery): 894M inst (+74M), stall 0.27. The +22M is CBU (control-flow branches around the dead `kInterpolationMinBins`/`m_have_precompute` interpolation code, which is dead at bins<512 but still compiled in).

**REGISTER/OCCUPANCY is the real lever (found via clean-build ncu, NOT -D-hook build):** at b16-sat F64, clean build: full BinSelect = **53 regs -> 3 blocks/SM -> 51.6% occ**; main = 40 regs -> 4 blocks -> 59.5%; **lean classify (BinSelectStaticLean) = 40 regs -> 61.8% occ** (beats main!). The full BinSelect's interpolation machinery (dead at bins<512 but still compiled) inflates registers +13, costing one resident block. SMEM identical (1.04KB). The earlier "full beats lean (0.27 vs 0.33 stall)" analysis was CONFOUNDED -- it used a -D-hook build where BOTH showed 40 regs, masking the occupancy gap. WARNING: -DCUB_HISTO_STATIC_SMEM_THREADS/ITEMS hooks change register allocation vs the clean source build; always verify regs/occupancy on the CLEAN (no-hook) build.

**FINAL CONFIG (exhaustively validated, LOCKED clocks): F64 range static = 384 threads / 8 items, PLAIN full BinSelect, NO launch_bounds min-blocks override.** I32 = 768, lean classify. This = main's exact launch config.

**RESOLVED — the sat-b16/b32 residual was NOT irreducible (I wrongly called it that twice; the user pushed, correctly).** FIX = single-ch wide F64 range static tier -> LEAN classify (BinSelectStaticLean) + `__launch_bounds__` min-3-blocks/SM on the static RANGE kernel (<512 threads). Mechanism: lean alone fits 40 regs but SPILLS the F64 level values in the hot UpperBound loop (STACK:24) -> 0.938; full avoids spill but needs 53 regs -> 51.6% occ -> 0.964. Pinning min-blocks=3 gives lean a ~56-reg budget -> it lands at REG:48 STACK:0 (NO spill) AND keeps 3 blocks/SM -> sat-b16 0.964->1.000, sat-b32 0.985->1.013, all 1M+sat parity-or-better (full-grid, all shapes, locked). min-blocks=4 FAILED earlier (forced <=42 regs -> spilled worse); 3 is the sweet spot. The launch_bounds is gated `PrivatizedSmemBins>0 && is_range_transform && static_smem_threads()<512 ? 3 : (>=512 ? 2 : 0)` so EVEN (is_range_transform=false, REG:40 unchanged) and the dynamic/>=512 paths are untouched. Agent gate simplified to: all static range -> lean (dropped the single-ch-F64-keeps-full exception). Files: agent_histogram.cuh gate ~464, kernel_histogram.cuh launch_bounds ~1580.

**(historical) The sat-b16/b32 residual — root cause pinned at SASS level (single-function precise extraction, clean build, locked):**
- main single-ch F64 b16 static kernel: 1808 insns, 40 reg, 0 stack-spill, 0 float-ops, 59.5% occ, 0.27 stall, 56 level-loads.
- branch FULL (shipping): 6328 insns, 53 reg, 0 spill, 190 float (dead interpolation guess/verify ladder COMPILED IN though dead at <=256 bins), 51.6% occ (53 reg -> 3 blk/SM vs main 4), 0.26 stall, 312 loads. Loses on OCCUPANCY + executes +74M insns.
- branch LEAN: 1960 insns (~main size!), 40 reg BUT spills STACK:24 IN THE HOT LOOP (LDL/STL interleaved with ATOMS.ADD), +115 NOP +48 LDCU (constant reloads main keeps in regs). 0.938x (worse than full -- hot-loop spill).
Both branch variants are heavier than main's hot loop: full can't fit 40 reg (needs 53), lean fits 40 but spills. The opcode MIX is near-identical to main (same 56 LDG, ISETP, IMAD) -- the diff is register-allocator quality: the branch's structurally-larger AgentHistogram class (700+ line diff: 3 ctors, hybrid/dynamic/gmem method surface, extra template params, warp_coalesce) gives nvcc a harder allocation problem even for the if-constexpr-pruned static path. NOT a tunable; would require shrinking the AgentHistogram class itself (large refactor, regression risk to the many now-passing cells). The 30 lean float-ops are in the COLD StoreOutput epilogue (16 threads, output PassThru identity roundtrip main elides) -- not the hot-loop cause.

Every lever tested & LOST to plain-full:
- lean classify (40reg/4blk but stall 0.33): WORSE everywhere (1M 0.95-0.98, sat 0.91-0.94) -- occupancy win < stall penalty.
- full + __launch_bounds__ min-blocks=4: forces regs 53->40 but SPILLS (STACK:16) -> WORSE everywhere (1M 0.98, sat-b16 0.943). Occupancy gain negated by spill.
- 640 threads: sat clean but ALL 1M regress ~0.97. 448/512: sat valley 0.88-0.94.
- items 10/12/16: collapse.
Mechanism: branch's restructured SmemPrivatizedKernel needs 53 regs for the full classifier (vs main's SweepKernel 40) -> 3 vs 4 blocks/SM -> 8% occ deficit, biting ONLY at the 2 most-contention-bound cells (b16/b32 saturated, atomics hammering ~1 SMEM bin). The 53 regs come from full BinSelect's interpolation ILP which ALSO gives the good stalls (0.27) -- inseparable. Hot path byte-identical to main; pure emergent codegen of the larger TU.

FINAL VALIDATED NUMBERS (locked, median-over-shapes, clean build): I32 range 1.05-1.28x ALL cells. F64 range: 1M all parity+ (1.004-1.026); sat b64/b256 parity+ (1.002-1.004); ONLY sat-b16=0.964 & sat-b32=0.985 regress. The user's '1M regression' was a CLOCK ARTIFACT (now clean). Net: single-ch range is parity-or-better everywhere except 2 saturated low-bin F64 cells (irreducible ~1.5-3.6%). EVEN F64+I32: all wins (~1.11), even-F64 temporal_phases at parity 1.01 (user's old concern, fixed).

**MULTI_RANGE F64 regression (~7% 1M low-bin, ~5% sat-b16) — FIXED & VALIDATED.** Cause: branch's 3-active-channel static SmemPrivatizedKernel SPILLS (REG:40 STACK:24, +11.7% inst, local_st=21312) vs main REG:39 STACK:0 -- the FULL BinSelect's dead interpolation code (kInterpolationMinBins branch never taken at <=256 bins) is replicated per-channel in the unrolled classify, pushing 3-channel reg pressure over budget. **FIX: route multi-channel (NumActiveChannels>=2) static range to BinSelectStaticLean** (the lean UpperBound-only classify) instead of full BinSelect -- removes the dead code -> REG:39 STACK:0 (=main). NOTE the fix is the CLASSIFY METHOD, not struct field-strip (kernel_histogram.cuh field #if guards were reverted; the multi-LEAN_ALL recovery came purely from the agent gate routing to BinSelectStaticLean). Validated locked clean build: multi F64 1M 0.995-0.998, sat 0.990-0.993 (was 0.925-0.948). multi I32 stays ~0.99.

**Final gate (agent_histogram.cuh ~464):** `is_range_transform && (sizeof(SampleT)<=4 || NumActiveChannels>=2 || CUB_HISTO_STATIC_RANGE_LEAN_ALL)` -> lean; else (single-ch wide F64) -> full BinSelect. Single-ch F64 keeps full because there it does NOT spill (1 channel) and full's dead-code ILP hides latency (lean RAISES stalls 0.27->0.34 -> 5% slower at sat low-bin). So: single-ch F64 = full (53reg, sat-b16=0.963 irreducible residual); everything else range = lean.

**THE THREAD COUNT IS THE LEVER, and it is NON-MONOTONIC.** Threads sweep @items=8, F64 b16-sat ratio vs main: t256=0.948 t384=0.969 t512=0.949 **t640=1.011** t768=1.006. 384 is a LOCAL dip, NOT the optimum. **t=640 makes F64 saturated FULLY parity-or-better: b16=1.011 b32=1.019 b64=1.029 b256=1.007** (every cell >=1.007). Occupancy: 640->3 blocks/SM=1920 (93.75%, same as 384); 768->2 blocks=1536 (75%, explains 768's 1M collapse to 0.895). 512->4 blocks=2048(100%) but worse at b16-sat. So 640 keeps high occupancy AND wins low-bin. items MUST stay 8 (t_scale(16)); items 10/12/16 collapse both sat and 1M. The branch's restructured kernel has more diffuse per-warp instruction scheduling than main's sweep kernel, so it NEEDS the extra warps (640 vs 384) to hide atomic/load latency at low-bin contention cells -- main's leaner per-warp stream didn't. Tradeoff: t640 b16_1M dips slightly (~0.987 in focused sweep; confirm in comprehensive). Set static_threads=640 for F64 (8B), keep 768 for I32 (4B, lean wins 1.07-1.28x at every cell).

The branch's `SearchTransform` carries 8 interpolation fields (m_inv_scale/m_first/m_last/m_have_precompute/m_mid/m_inv_scale_lo/m_inv_scale_hi/m_mid_bin) main lacks — only used by dynamic/cooperative/cache kernels (which call PrecomputeOnDevice); dead for the static kernel. Suspected but UNPROVEN as the residual cause; stripping them behind `CUB_HISTO_STATIC_RANGE_LEAN_ALL` was set up but not the chosen fix.
