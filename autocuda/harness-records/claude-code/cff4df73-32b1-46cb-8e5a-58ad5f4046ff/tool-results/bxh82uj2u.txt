metadata:

In the qr_v2 run, the idea of **co-batching MB matrices' `W=VᵀA` trailing-reduction into one CTA** (to fill the parallelism-starved schedulers — the trailing's W=VᵀA has tiny 32×32 output but deep K, leaving 61% no-eligible-warps) **REGRESSES in Triton** (W2 brief-22, measured on n=1024, ncu-rooted).

**Why:** the Triton trailing CTA ALREADY maps ONE matrix's `tl.dot` across ALL its warps. Adding a 2nd matrix's dot adds NO schedulable warp — only a live W accumulator → +register pressure → occupancy HALVES (151→255 regs/thread, Block Limit 6→2 blocks/SM, eligible warps 0.27→0.17, time 176→235µs). MB=2/3/4 all worse; ~18 configs swept. The fill the starvation needs is MORE blocks/SM (SMALLER footprint), the OPPOSITE of co-batch.

**The crux:** **Triton cannot pin disjoint warp-subsets to different matrices.** A CUDA/WMMA kernel CAN (assign warp-group 0 to matrix A, warp-group 1 to matrix B), so a CUDA co-batch MIGHT escape this wall where Triton can't. If pursuing co-batch, it MUST be hand-CUDA with explicit per-matrix warp assignment — not Triton.

**How to apply:** don't co-batch in Triton. The n=512/n=1024 trailing W-reduction starvation is real but unfixable by Triton co-batch. Either accept the trailing floor, or attempt CUDA-WMMA co-batch with disjoint warp-groups per matrix (unproven, high effort). Also: at n=1024 only the PANEL is grid-starved; the trailing grid is SATURATED (3.24 waves). See [[qr-v2-run-state]].
