# Skill Report: 2026-06-22-09-10-03-qr_v2

## Executive Summary

The automated audit of the `2026-06-22-09-10-03-qr_v2` run produced **221 candidate rows**, of which **172 are missing-harness coverage gaps** (the four worker sub-agent session JSONLs were never passed to the data step — only the manager session was scanned) and **49 are real signals from the manager session**. After triaging every non-coverage row against the cited harness context, **zero confirmed autocuda *skill* implementation bugs** survive: the 20 `autocuda_cli_contract` rows are all `--help` / log-tail probes (the scanner matched the literal `error:` / `invalid choice` strings inside help text, not actual command rejections), the 16 `autocuda_exception` "tracebacks" come from the agent manually running `python eval.py` from a worktree without `utils.py` on `PYTHONPATH` (a setup/usage issue, not an autocuda crash), and 9 of the 9 `explicit_skill_issue` rows are worker optimization outcomes or the manager's own self-reflection. The single behaviorally real finding is the **operator-confirmation gate** (4 rows, one incident): mid-run the manager paused to ask the operator which worker to redirect instead of continuing the never-stop loop.

Key takeaways:

- **No skill code bug.** No SKILL.md instruction or skill→CLI contract caused a failure in this run; the implicated skill is `optimize-tree`, and its contract held.
- **Coverage is the dominant gap.** 172/221 rows (78%) are missing-harness placeholders for the four workers' brief branches; the audit only saw the manager's `optimize-tree` session, so worker-side skill friction is unmeasured.
- **The CLI-contract cluster is a false-positive class.** All 20 rows are the manager discovering the CLI surface (`autocuda log optimize-tree --help`, `autocuda brief` → "invalid choice", `autocuda run --help`); each was immediately self-corrected. At most this is a CLI *discoverability* nit, not a contract break.
- **The "critical" exception cluster is a project-harness/usage issue, not autocuda.** 16 rows are one recurring `ModuleNotFoundError: No module named 'utils'` from `eval.py` when the manager validated a kernel from a scratch worktree's problem dir without the set-root on `PYTHONPATH`; the agent diagnosed `env.sh`'s `PYTHONPATH` logic and fixed its own invocation. Severity downgraded from critical to low.
- **One genuine confirmation gate.** At `2026-06-24T14:51:18Z` the manager answered an operator question and ended its turn with "Want me to redirect a second worker… or keep…?", and explicitly acknowledged it had under-prioritized replying — a mild stop-for-confirmation against the never-stop directive.

## Root Causes

Grouped by the cause the candidates point to:

- **Coverage gap — missing worker harness mapping (172 rows, info).** The data step was given only the manager Claude Code session (`…/cff4df73-…jsonl`). The four `optimize-tree-worker` sub-agents that executed `explore-brief` for each of the 172 brief branches were not passed, so every `worker-N-brief-M` branch produced a `missing_harness` placeholder. This is the largest single contributor to the row count and the only thing preventing a complete audit. Not a bug — a data-collection gap.

- **CLI-discoverability false positives — `optimize-tree` SKILL.md (20 rows; 18 false positives, 2 minor).** The scanner's keyword match on `error:` / `invalid choice` / `the following arguments are required` fires on three distinct *probes*, not rejections: (1) `autocuda log optimize-tree --help` output (L1168), whose usage example literally contains "error: the following arguments are required"; (2) `autocuda log` manager-log tails and `autocuda run --help` (L9645); and (3) the one substantive case, L6847, where the manager guessed `autocuda brief` (got "invalid choice") before finding `autocuda log optimize-tree brief`. The only actionable item is that the `brief` subcommand path could be spelled out in the SKILL.md so the agent does not guess. No CLI contract was actually violated.

- **Setup prerequisite — validate invocation / `PYTHONPATH` (16 rows, downgraded critical→low).** The recurring `ModuleNotFoundError: No module named 'utils'` (L9196, L9201) is `eval.py` failing its `from utils import …` because the manager ran `python eval.py test .` from a scratch worktree's `problems/linalg/qr_v2/` dir, where `utils.py` (at the set root `problems/linalg/`) was not on `PYTHONPATH`. `env.sh` normally exports `PYTHONPATH="$PROBLEM_DIR:$EVAL_DIR:$UTILS_DIR…"`; the bare `python eval.py` bypassed it. The traceback is from the problem's `eval.py`, merely wrapped by `autocuda run exclusive --` (a GPU-lock shim) — autocuda itself did not raise. This is a setup/usage prerequisite the manager had to rediscover mid-run, so it belongs in the discover/optimize-tree setup notes, but it is not an autocuda exception.

- **Manager self-correction & reflection, not skill defects (9 `explicit_skill_issue` rows).** bug_0177 is a worker's FP4 negative result plus an upstream Triton/MLIR compile bug (normal optimization failure). bug_0184–0185 are the manager admitting its *own* repeated "graft d60e14e6" instruction violated the skill's no-cross-tag-peek rule — the rule was correct, the agent was wrong, and it fixed its memory. bug_0186–0191 are the manager re-reading the operating rules and confirming alignment; the "submit bug" it fixed is in the **project's `harness/submit.sh`** ($REPO_DIR via BASH_SOURCE), not any autocuda skill. None implicate skill instructions or the skill→CLI contract.

- **Confirmation-gate behavior — `optimize-tree` never-stop section (4 rows, one incident, low).** At L8601 the manager, after answering an operator's "did you read the report?" question, ended its turn with an open choice ("Want me to redirect a second worker… or keep…?") and acknowledged it had been "treating your messages as steering… under-prioritized replying." In an autonomous never-stop run this is a (mild) stop-for-confirmation: the operator's original launch instruction should have been treated as the standing greenlight to keep dispatching briefs. This is the only behavioral finding attributable to skill guidance.

## Fix Plan

Concrete edits, smallest-impact first. None require changing kernel or skill files in *this* repo (the report is read-only); these are recommendations for the autocuda skill maintainer.

1. **Close the coverage gap (data, not skill).** Export the four worker sub-agent session JSONLs into `autocuda/harness-records/` and re-run:
   ```bash
   eval "$(autocuda report data skill --tag 2026-06-22-09-10-03-qr_v2 \
       --harness-jsonl <worker-branch>=<jsonl-path> ...)"
   autocuda schema check report-skill-csv --output 2026-06-22-09-10-03-qr_v2
   ```
   Validation: the regenerated CSV has < 172 `missing_harness` rows and the schema check passes.

2. **optimize-tree SKILL.md — spell out the brief-post command.** Add the exact `autocuda log optimize-tree brief --agent-id <id> …` invocation (and note that `autocuda log optimize-tree {baseline,brief,iteration,start,stop}` is the lifecycle surface) so the agent does not guess `autocuda brief`.
   Validation: `autocuda log optimize-tree brief --help` matches the SKILL.md example verbatim.

3. **discover / optimize-tree SKILL.md — document the validate prerequisite.** State that ad-hoc `python eval.py …` must run from the set-root dir (or with `PYTHONPATH` set as `env.sh` does, because `utils.py` lives at `problems/<set>/`), so a manager validating a worktree commit does not hit `ModuleNotFoundError: No module named 'utils'`.
   Validation: a from-set-root `python eval.py test <problem-dir>` (or `PYTHONPATH=<set-root> …`) runs without the import error.

4. **optimize-tree never-stop section — treat the launch instruction as a standing greenlight.** Add explicit guidance: answer operator questions inline, then immediately resume dispatching briefs; do not end a turn on an open "should I…?" choice unless the operator has paused the run.
   Validation: a never-stop transcript review shows no turn ending in an operator-directed choice while the run is active.

5. **report-skill data step (CLI) — reduce help/log-tail false positives (optional).** The `autocuda_cli_contract` and `autocuda_exception` heuristics fired on `--help` output, log-row description text, and a problem-script traceback wrapped by `autocuda run`. Consider excluding lines that are clearly `--help` usage blocks or `autocuda log` CSV tails, and distinguishing a traceback whose top frame is the autocuda package from one whose top frame is the problem's `eval.py`.
   Validation: re-running the data step over this manager JSONL yields fewer than the current 36 (20 CLI + 16 exception) non-coverage candidates, with the genuine confirmation gate retained.
