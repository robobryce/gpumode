Cost Report: 2026-06-25-22-03-01-qr_v2

Executive Summary

This was an inexpensive run in absolute terms: a 3-worker parallel tree-search optimize over linalg/qr_v2, ≈17.8 h of wall-clock (2026-06-25 22:00 → 2026-06-26 15:51 UTC) on a single shared B200, costing roughly $1.3K in inference at Claude Opus 4.8 list rates and burning ≈1.35B tokens. As with every run of this shape, the cost is dominated by inference, not GPU time — the fleet read 1.25B cached-context tokens and wrote 105M new cache tokens, so ≈98 % of the spend is cache traffic; the actual GPU benchmark/build work was only ≈2.1 h of device time, and output generation was a rounding error (≈$28). Because this is a single experiment with no cross-run comparison, treat the figures as a standalone profile rather than a benchmark — there is no second run here to normalize against.

Key takeaways

  • Inference dominated, GPU did not. ≈$1.3K inference vs. ≈2.1 h of measured GPU build/benchmark time; the spend tracks token volume, not device hours.
  • Cache reads + cache writes are ≈98 % of the bill. Cache write $657 (50 %) + cache read $623 (47 %); uncached input ($3) and output ($28) are negligible.
  • Cache hit rate was 92.2 % — healthy. The prompt prefix (SKILL.md + brief context) is being reused well rather than re-read cold each trial, so there is no low-hanging cache-restructuring win. Cache creation ($657), not cache read, is the single largest cost line.
  • Heavy de-duplication was required. The raw usage sums double-count streamed/resumed records ≈2×; deduping by message id halves the apparent cost from ≈$2.6K to ≈$1.3K. The figures below are all deduped.
  • Walltime was GPU-light and stall-light. Only ≈2.1 h of device hold and ≈0.9 h of lock-wait across the 17.8 h calendar — the rest is inference latency and brief-internal reasoning, not benchmark queueing (a 3-on-1 fleet contends far less than the prior 4-on-1 run).

One-liner: ≈17.8 h wall-clock, ≈$1.3K inference (Opus 4.8 list rates), ≈1.35B tokens in/out (1.25B cache-read, 105M cache-create, 0.6M uncached input, 1.1M output), 3 compactions. The cost is in line with environment.md’s timeout envelope — per-call GPU budgets bounded device time to ≈2.1 h despite 52 branches, so no single trial ran away on the GPU.

Cost-Optimization Opportunities

  • Cache creation is the single biggest cost line (105M tokens, $657). Each new brief and each sub-agent/worker restart writes a fresh cache prefix at 1.25× the input rate. 52 branches (24 substantive + 28 zero-trial) plus ≈67 utility sub-agents means a lot of prefix re-writes; consolidating related objectives into fewer, longer-lived briefs — and cutting the 28 zero-trial briefs — would amortize the write premium. This is the highest- leverage inference lever on the run.
  • Web tool usage is on the higher side (467 WebFetch+WebSearch calls). The agents reached to the web for references more than a pure-training-data run; each fetch adds a large uncached chunk to the next prompt (feeding cache-creation cost) and adds latency. Tightening the skill prose to lean on built-in CUDA/Householder knowledge for the common cases would trim both.
  • Cache hit rate is already high (92.2 %) — no action. This is normally the top cost lever on a long run, but here it is healthy; do not restructure the skill prose for caching.
  • Bench/build device time is tiny (2.1 h) and not a cost driver. The ≤180 s bench and ≤600 s profile budgets bounded GPU time well; the ≈0.9 h of lock-wait is wall-clock, not inference, and is small on a 3-on-1 fleet — no GPU-side cost action needed.
  • Per-worker view (optimize-tree). The harness emitted one combined steering session, so per-worker-branch token attribution isn’t available from the CSV; at the role level no group exceeds the other by the 2× runaway threshold in a way that indicates a stuck loop — the sub-agent aggregate is large because it is ≈70 sessions, not one runaway. (Pass --harness-jsonl <branch>=<path> per worker session in a future report data cost run to get a true per-worker split.)

Analysis

The cost shape is the familiar context-heavy, GPU-light agentic search: 1.25B cache-read tokens against just 1.1M output tokens means the fleet spent its budget re-reading its own accumulated context far more than generating new text or running the device. At Opus 4.8 list rates this lands at ≈$1.3K, of which ≈98 % is cache traffic (write $657 + read $623). The GPU — the nominal object of the experiment — accounts for only ≈2.1 h of measured device work, well inside environment.md’s per-call budgets, so no single trial ran away on hardware. The ≈0.9 h of lock-wait confirms the documented contention on the shared B200 is mild at 3-on-1 (the prior 4-on-1 run paid ≈9.5 h of lock-wait); that queueing is free in inference terms (agent idle time, attributed to neither inference nor billed GPU).

The most important methodological note is de-duplication. The raw usage blocks in these JSONLs double-count streamed/resumed assistant records almost exactly 2× (7,221 raw rows → 3,590 unique message ids), which would have inflated the headline from ≈$1.3K to ≈$2.6K. Every figure in this report is deduped by message id; an analyst pulling raw sums from the same files should expect roughly double these numbers. This is also why a direct comparison to the 06-22 report (which reported ≈$3.3K on a 56 h / 4-worker run) should be read carefully: this run is genuinely cheaper (shorter, one fewer worker, fewer branches), but the cache-traffic fraction (≈98 %) and high hit rate (≈92 %) are the same structural signature.

Where did the cost concentrate? Not on the manager (a lean $108) but across the ≈70 sub-agent sessions ($1,204 combined). That inverts the prior run’s pattern and is the right shape: the manager here stayed terse (632K output, 0 compactions) while the workers and the many report/audit/consult helpers did the token-heavy work — reading large profiles, web references, and accumulated branch context. The 3 compactions all landed in long sub-agent sessions, consistent with workers (not the manager) hitting the context window on the heavy-shape briefs.

Recommendations. (1) Cut cache-creation volume — the largest line at $657 — by consolidating objectives into fewer, longer-lived briefs and eliminating the 28 zero-trial briefs; each brief/restart pays a fresh 1.25× cache-write premium. (2) Reduce web tool reliance (467 fetch/search calls) by tightening skill prose to lean on built-in CUDA knowledge for routine QR/Householder reasoning, trimming both the uncached input that feeds cache-creation and the added latency. (3) For a future run, pass --harness-jsonl <branch>=<path> per worker session to report data cost so per-worker spend is attributed in the CSV and a runaway worker (if any) is named automatically — this run’s single combined session forced a role-level rollup instead.
