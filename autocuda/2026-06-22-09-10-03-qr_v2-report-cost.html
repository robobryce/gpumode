Cost Report: 2026-06-22-09-10-03-qr_v2

Executive Summary

This was a moderately expensive run in absolute terms: a 4-worker parallel tree-search optimize over linalg/qr_v2, ~2.3 days of wall-clock (2026-06-22 09:05 → 2026-06-24 18:13 UTC) on a single shared B200, costing roughly $3.3K in inference at Claude Opus 4.8 list rates and burning ~3.67B tokens. The cost is dominated by inference, not GPU time — the fleet read 3.43B cached-context tokens and wrote 230M new cache tokens, so 96% of the spend is cache traffic; the actual GPU benchmark/build work was only ~16 hours of device time, and output generation was a rounding error (~$101). Because this is a single experiment with no cross-run comparison, treat the figures as a standalone profile rather than a benchmark — there is no second run here to normalize against.

Key takeaways - Inference dominated, GPU did not. ~$3.3K inference vs. ~16.0 h of measured GPU benchmark/build time; the spend tracks token volume, not device hours. - Cache reads + cache writes are 96% of the bill. Cache read $1.71K (52%) + cache creation $1.44K (44%); uncached input ($11) and output ($101) are negligible. - Cache hit rate was high — 93.6%. This is a healthy number for a long agentic run; the prompt prefix (SKILL.md + brief context) is being reused well rather than re-read cold each trial, so there is no low-hanging cache-restructuring win. - The manager is the single most expensive session ($976, 30% of spend). It stays alive the whole run accumulating a long cached context; the four workers cost $388–$526 each and 170 utility/report sub-agents cost $474 combined. - GPU time is benchmark-bound, with real contention. Exclusive GPU calls (bench/profile/validate) ran 15.4 h across 1,159 calls vs. 0.6 h of builds; lock-wait on the shared B200 added ~9.5 h of queueing.

One-liner: ~57 h wall-clock, ~$3.3K inference (Opus 4.8 list rates), 3.67B tokens in/out (3.43B cache-read, 230M cache-create, 2.2M uncached input, 4.0M output), 5 compactions. The cost is in line with environment.md’s timeout envelope — per-call GPU budgets (180 s bench, 300–600 s profile) bounded device time to ~16 h despite 172 branches, so no single trial ran away on the GPU.

Cost-Optimization Opportunities

  • Manager output volume. The manager emitted 2.92M output tokens — ~18× the median worker (0.16M) — almost all of it brief-writing and steering narration. Tightening the manager’s per-brief prose (shorter briefs, fewer restated objectives) is the most direct output-cost lever, though output is only $101 total so the savings are small.
  • Cache creation is the second-biggest line (230M tokens, $1.44K). Each new brief and each worker restart writes a fresh cache prefix. Workers that churned through many short briefs (worker-2: 39.1M cache-create on 25 briefs) pay proportionally more cache-write premium; consolidating related objectives into fewer, longer-lived briefs would amortize the write cost.
  • Bench-call count >> build-call count (1,159 vs. 684). Benchmarking/validation dominates GPU time (15.4 h vs. 0.6 h builds). The 180 s task.yml bench timeout already bounds this, but 1,159 exclusive-GPU calls against a single shared device also generated 9.5 h of lock-wait — adding GPUs (or capping concurrent benchmarks) would cut queueing wall-clock, not inference cost.
  • Cache hit rate is already high (93.6%) — no action. This is normally the top cost lever on a long run, but here it is healthy; do not restructure the skill prose for caching.
  • Per-worker view (optimize-tree). Worker costs are tightly clustered ($388–$526, median $452); no worker exceeds 2× the fleet median, so there is no runaway loop or stuck profiler to name. Worker-0 is the most expensive ($526) and also ran the single longest brief (brief-44, 5.72 h) — expensive because productive, not because stuck.

Analysis

The cost shape is that of a context-heavy, GPU-light agentic search: 3.43B cache-read tokens against just 4.0M output tokens means the fleet spent its budget re-reading its own accumulated context far more than generating new text or running the device. At Opus 4.8 list rates this lands at ~$3.3K, of which 96% is cache traffic (read $1.71K + write $1.44K). The GPU — the nominal object of the experiment — accounts for only ~16 h of measured device work across 1,843 lock acquisitions, well inside environment.md’s per-call budgets (≤180 s bench, ≤600 s profile), so no single trial ran away on hardware. The 9.5 h of lock-wait confirms the documented 4-way contention on the shared B200: the run was frequently GPU-queue-bound in wall-clock, but that queueing is free in inference terms (it is agent idle time, attributed to neither inference nor billed GPU).

Was the spend justified by the result? The companion optimization report for this tag records a 63.33× speedup (torch.geqrf baseline 131,465 µs → 2,075.9 µs geomean, commit 76204dd5), driven by replacing the serial cuSOLVER loop with a custom batch-major blocked Householder kernel and stacking fused-trailing + tensor-core + graph-capture refinements on top. Against a 35× improvement over the prior library-routing run, ~$3.3K of inference for a #1-class kernel is a favorable trade — the decisive structural win (7f5cdc08, 10.8× in a single commit) and its descendants came out of exactly the kind of broad, diverse brief search this cost profile reflects.

Did inference grow super-linearly with trial count? Not visibly: the four workers are tightly clustered in cost ($388–$526) despite very different brief counts (worker-0: 47 briefs, worker-3: 21), which means cost scales with cached-context size and session lifetime, not raw trial count — context is being recycled (93.6% hit rate), not rebuilt per trial. The most expensive session is the manager ($976), not any single productive worker, because steering is continuous for the full 2.3 days while each worker’s context resets at brief boundaries. The most expensive worker (worker-0, $526) is also the one that ran the single longest and one of the most productive briefs (brief-44, 5.72 h), so here the expensive branch is the productive branch rather than a stuck one.

Recommendations. (1) Cut cache-creation volume by consolidating related objectives into fewer, longer-lived briefs — each brief/restart pays a fresh cache-write premium, and cache creation is the second-largest cost line at $1.44K. (2) Trim manager output — shorter, less-repetitive brief prose on the single most expensive session, the one row carrying ~18× the median worker’s output. (3) For wall-clock (not inference) reduction, add GPU capacity or cap concurrent benchmarks to drain the 9.5 h of lock-wait on the shared B200; this shortens the 2.3-day calendar without changing the bill.
