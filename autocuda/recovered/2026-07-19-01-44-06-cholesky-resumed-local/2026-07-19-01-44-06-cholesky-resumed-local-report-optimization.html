At the 2026-07-19 09:06:31 UTC snapshot, the five-worker tree had reduced the B200 benchmark geomean from 2153.690 µs to 972.969 µs, a 2.2135× speedup and 54.82% latency reduction. Computational Description

Problem Overview

The kernel factors a batch of independent dense FP32 symmetric positive-definite matrices. For input A with shape batch × n × n, it must return a lower-triangular FP32 matrix L with a positive diagonal such that A ≈ L Lᵀ; validation checks the reconstruction, triangular structure, finiteness, dtype, and device rather than requiring bitwise agreement with one library. A Cholesky factorization performs approximately n³/3 floating-point operations per matrix and stores O(n²) values, so a batch costs approximately batch × n³/3 FLOPs.

The B200 benchmark contains 15 inputs spanning n=32 through n=32768. Its first six entries, from (batch=4096, n=32) through (batch=4, n=1024), each contain 2²² FP32 input elements, which holds the 16 MiB input footprint constant while increasing the work per element. Additional high-batch n=512/1024/2048/4096 entries test throughput and occupancy separately, while the single-matrix n=8192/16384/32768 entries expose large-factorization efficiency. The score is the geometric mean of all 15 runtimes, so improving one regime cannot compensate efficiently for regressing another.

Computational Phases

For a blocked right-looking Cholesky with panel width b and remaining trailing order m, the computation repeats the following dependency chain. The small persistent kernels fuse these phases inside one CTA, while the library and CuTe paths express them as separate operations.

Phase High-level operation Cost and parallel structure
1. Dispatch and storage preparation Select the shape-specific path; acquire cached output, solver workspace, info buffers, and pointer tables; copy the required input triangle into the factor buffer. O(batch × n²) data movement plus fixed allocation/dispatch/launch latency.
2. Diagonal-panel factorization (POTRF) Factor the current b × b diagonal block in FP32 so subsequent work has a numerically stable panel. About O(batch × b³) per panel. Panels are sequential because panel k+1 depends on the preceding update; parallelism exists within a panel and across matrices.
3. Panel triangular solve (TRSM) Solve for the block column below the diagonal factor, producing L₂₁. About O(batch × m × b²) per panel. Rows and batch members are parallel, but the solve remains on the panel critical path.
4. Trailing rank-k update Apply the Schur-complement update A₂₂ ← A₂₂ − L₂₁ L₂₁ᵀ, using GEMM/RankK or a fused device update. About O(batch × m² × b) per panel and most of the aggregate batch × n³/3 work. Trailing tiles and batch members provide the widest parallelism.
5. Output finalization Copy or transpose the physical factor representation and zero any logical upper-triangular values touched by full GEMMs. O(batch × n²) bandwidth work; avoidable whole-matrix passes can be visible once factorization is fast.

Performance Model and Bottlenecks

An ideal factorization’s arithmetic intensity rises with n: approximately n/12 FLOP/byte if only the required input and output triangles cross HBM, or n/24 FLOP/byte if full input and output buffers do, before accounting for extra panel rereads. That linear growth explains why one performance model does not fit the grid. Small n has too little work per launch to approach a compute roof; large n has enough reuse in GEMM-like trailing updates to become compute-dominated; and the sequential POTRF/TRSM panel chain imposes a latency floor even when the update is highly parallel. Copies, conversions, pointer construction, and triangular cleanup remain O(n²) bandwidth-bound phases across every regime.

Shape regime Primary bottleneck Performance model and evidence
n=32/64/128; batch=4096/1024/256 Launch, synchronization, and instruction latency; not peak math throughput The entire footprint is only 16 MiB and each matrix has little arithmetic. Grouping matrices per CTA, keeping rows in registers/shared memory, and using warp shuffles produced the run’s largest marginal gain, showing that library dispatch and fine-grained synchronization dominated.
n=256/512; batch=64/640 Launch/intermediate-traffic overhead plus occupancy One persistent CTA per matrix exposes enough independent matrices to fill the GPU while keeping POTRF/TRSM/update sequencing on device. The large MathDx wins indicate that eliminating repeated host/library launches and intermediate traffic mattered as much as raw FLOPs.
n=512–4096; batch=1–16 Mixed solver-compute and latency regime Direct BF16x9 cuSOLVER usually won because its optimized POTRF outweighed the conversion and multi-launch costs of a custom blocked path. Persistent outputs/workspaces and the choice between batched and looped POTRF remained material, so this region is not purely compute-bound.
n=1024/2048; batch=60/8 Batched panel critical path with compute-heavy trailing updates Grouped POTRF/TRSM and tensor-core GEMM improve throughput across matrices, but each panel still waits for the previous Schur update. Pointer-table reuse, compact panels, and cleanup kernels reduce the non-compute floor.
n=8192/16384/32768; batch=1 Primarily tensor-core compute-bound, with a serial panel floor The O(n³) lower-triangular RankK dominates and amortizes FP16 conversion, making a persistent CuTe tensor-core update profitable. FP32 POTRF/TRSM, panel conversion, and final copies are lower-order but form the remaining Amdahl-limited critical path.

These classifications are an analytical model supported by the trial outcomes and per-shape timings, not a counter-derived roofline measurement: hosted profiling was unavailable at the snapshot, so achieved bandwidth, tensor-core utilization, occupancy, and launch gaps were not measured directly.

Register/shared-memory kernels for n=32/64/128. The final n=32 path groups four matrices into one 128-thread CTA, gives each matrix a warp, retains row values in registers, and recursively unrolls the 32 Cholesky steps with warp shuffles. The n=64 path groups two matrices per CTA in padded shared tiles, while n=128 uses one 512-thread CTA with four lanes per row so each thread owns 32 values rather than an entire row. This replaces generic solver setup and global-memory coordination with one resident block and cheap warp/block synchronization, which is the right bottleneck trade for thousands of tiny matrices. 1428d299 widened n=128 row teams from two to four threads and moved that cell from 69.938 to 61.549 µs; 63508924 then made staging coalesced and removed repeated row/column decoding. Eight branches independently revisited this surface, so the family is strongly supported rather than a one-off graft. It stands alone for n≤128 and stacks with the broader dispatcher through disjoint shape coverage.

Persistent buffers plus direct cuSOLVER/BF16x9. The middle-shape path keeps PyTorch’s current cuSOLVER handle on the caller stream but removes repeated framework work around it. 9ce7e5f1 changed the wrapper from allocating or cloning an output on every call to copying into a shape- and input-scoped persistent buffer; the same cache retains the device pointer array, info, and solver workspace. The wrapper chooses SpotrfBatched for larger batches and serial Spotrf calls with one shared workspace for batch≤4. 20835bf5 additionally sets CUSOLVER_FP32_EMULATED_BF16X9_MATH before both workspace sizing and execution, cutting n=32768 in that branch from 215173.793 to 132299.355 µs. The important follow-up was dispatch, not a universal library claim: 55d801d0 kept direct BF16x9 at n=2048/n=4096, where it beat the mixed path by as much as roughly 2×, and reserved blocked CuTe for larger or more highly batched work. Ten branches explored this family. Its 1.6521× peak is a parent-relative ranking signal and includes setup/crossover context, not a pure solver-math attribution.

Shape-specific composition and dispatch. The aggregate winner is a portfolio assembled from non-overlapping local winners. By the snapshot, custom_kernel routes n=32/64/128 to dedicated extension kernels, batch-64 n=256 and batch-640 n=512 to persistent MathDx, batch-60 n=1024 to a 256-column high-batch panel algorithm, batch-8 n=2048 to grouped blocked cuSOLVER/cuBLAS, single-batch n≥8192 to mixed-precision CuTe, and the remaining middle cells to direct cuSOLVER. 9d7af0d6 demonstrated the value of composition by merging the n=512 MathDx path with the grouped n=2048 path without taxing unrelated cells; e0349c9b added the n=1024 high-batch panel route. Mechanically, the dispatcher also selects zeroed versus uninitialized cached outputs and prepares only the workspace or pointer tables needed by the chosen path. This technique’s 1.6455× peak comes from a bundled combine step, while 2.1559× is the stack’s cumulative speedup, so neither should be read as the gain from a single if. Twelve combine briefs and 139 grouped observations show that integration was a major search activity.

Persistent MathDx for high-batch n=512/n=256. These kernels keep an entire matrix’s left-looking Cholesky inside one CTA: MathDx performs device POTRF and triangular solves on each panel, and FP16-input/FP32-accumulate tensor-core GEMMs apply prior-panel updates. That removes the repeated Python, cuSOLVER, and cuBLAS launch sequence that dominates when hundreds of medium matrices are available to occupy the B200 concurrently. 644d05ec made the n=512 launch use PyTorch’s actual caller stream and improved the batch-640 cell from 1960.950 to 1935.286 µs. The later n=256 specialization in 4733dddb took its batch-64 cell from 300.985 to 178.401 µs and the full geomean from 999.771 to 974.583 µs; f6e9b180 widened tiles from 32 to 64 and reached 168.125 µs. The recorded 1.6167× family peak at 8879bfc4 bundles restoration of an n=32 schedule with the n=512 path, so the isolated n=256 measurements are cleaner evidence. Only two branches pursued MathDx deeply, making its measured wins strong but its prevalence less independently established.

Mixed-precision blocked Cholesky with triangular CuTe RankK. 436001ec introduced a right-looking blocked algorithm that keeps numerically sensitive diagonal POTRF and panel TRSM in FP32 while moving the O(n³) trailing update to tensor cores; its clean foundational step was 1.1713×. The final single-matrix large-n path uses 4096-column panels, converts the solved panel into a compact FP16 buffer, and feeds a Blackwell persistent CuTe scheduler that enumerates only lower-triangular output tiles instead of computing the unused upper half. f041bc22 added a tiled factor copy/transpose that reads the lower factor coalescently, writes the required output triangle, and zeros the logical upper triangle, moving the three large CuTe cells from 4772.662/14791.802/53321.911 to 4660.722/14559.581/52708.096 µs. This family stacks on the output/workspace caches and serves n≥8192, where conversion is amortized by much larger trailing updates. Thirteen branches explored it, the widest independent coverage in the run. The CSV’s 1.2915× peak belongs to bundled transplant be3e6750, which remeasured at 1077.830 µs versus its 1058.933 µs parent; treat that peak as noisy attribution rather than evidence that the packed converter itself won.

Prewarming, workspace reuse, and triangular cleanup. Once the algorithmic paths were in place, narrow setup and data-movement changes produced smaller but still stackable gains. 292b3f6f preallocated four grouped n=2048 outputs and their pointer tables during the untimed shape transition, avoiding allocator and table-construction work in measured calls; its aggregate movement was only 1039.324 to 1035.688 µs, consistent with a micro-optimization near the 1.765% run-noise scale. 2d5d0889 replaced a generic tril_ only for batch-60 n=1024 with a caller-stream float4 kernel that zeros the upper triangle in place, reducing that cell from 2264.428 to 2158.279 µs. The largest clear member, 4057017e, replaced batched PyTorch panel factorization at batch-2 n=4096 with compact column-major factor buffers, persistent cuSOLVER workspace, and two serial BF16x9 POTRF calls per panel; the cell fell from 7709.368 to 3852.275 µs and aggregate from 1069.313 to 1015.759 µs. Ten branches worked this family, but its mechanisms are shape-local refinements that depend on the larger dispatcher rather than a standalone algorithm.

Failed Optimization Techniques

The 41 failed structured trials comprised 14 validation errors, 9 build errors, and 18 runtime errors; the report data clusters them into 33 failed technique rows.

Illegal secondary-stream schedules. Batch sharding across explicit CUDA streams was repeatedly incompatible with the benchmark’s mandatory caller-stream policy. Four-way scheduling (f2d11c5d), per-matrix handles/streams/events (aa18342d), and eight-way scheduling (6247fd2f) were rejected before a trustworthy benchmark could be recorded. This is a portability failure, not evidence that concurrency lacks value: any future version must express overlap through legal caller-stream kernels, persistent CTAs, or library grouping rather than creating private streams.

Layout-sensitive CUTLASS/CuTe rewrites. Several attempts changed tile geometry, epilogues, or operand layout without preserving every alignment and triangular-coverage invariant. 7057d474 hit a vector-epilogue/scalar-iterator compile mismatch, cb456e9d produced a misaligned address at n=8192, 8d52c7e9 mixed row- and column-major strides, and c9bdb065 omitted tiles in an asymmetric rectangular schedule, producing reconstruction residuals of 0.255–0.339. 3ce85c8b’s direct FP32-to-FP16 TMA conversion reached an illegal instruction (XID 13). These failures indicate that future CuTe work needs explicit layout proofs and small coverage tests before a full remote run, especially around the diagonal and tail tiles.

Numerically unsafe or structurally incomplete factorization. Lower-triangle-only storage and aggressive reduced precision failed when later operations still read or wrote the opposite half. c87292ef allowed a batch-60 GEMM to pollute the upper triangle, f70090d5 left a 0.981 lower-factor residual at batch-2 n=4096, and d142afb0 still failed because diagonal CuTe tiles wrote upper elements despite zero initialization. A TF32 WMMA n=256 rewrite (daa5ee3b) produced NaN/Inf after its approximate Schur complements lost positive definiteness. bd9fb59f invoked Xpotrf for only the first batch member, yielding residuals of 0.881 and 8.43. Keeping panel POTRF/TRSM in FP32 and validating every batch member were therefore necessary, not conservative overhead that could simply be deleted.

Over-fused kernels and compile/resource pressure. Attempts to hold progressively larger matrices in one CTA crossed hard device or compilation limits. 20bc0a8d requested 66048 bytes of static shared memory against a 48 KiB limit, 2050b6ec needed an unavailable default dynamic-shared allocation, and 66dd27dd/745c67ad exhausted launch resources at 1024/384 threads. Other literal-unrolled or large generated kernels spent more than ten minutes in JIT compilation, while one high-batch variant (60e65542) ran for 1846 seconds. The viable persistent kernels succeeded by limiting residency to n=256/n=512 and using tiled MathDx operations, not by materializing a full larger factorization in registers or shared memory.

Conversion-free and SYRK substitutions. Removing compact FP16 panel staging looked attractive but generally cost more in memory traffic or could not satisfy the tensor-core layout. The direct TMA converter crashed, while other direct-FP32 variants preserved correctness but regressed against explicit compact staging. A scalar triangular SYRK route first hit missing cuBLAS linkage (0e76423c); after linkage was repaired, 3ed44543 was materially slower than the full tensor-core GEMM path despite updating fewer mathematical elements. Replacing it with cublasGemmStridedBatchedEx recovered performance, showing that tensor-core throughput outweighed the nominal arithmetic saved by scalar triangular SYRK.

Unexplored Areas

Kernel-level profiling. No hosted profile was available because the BREV profiler URL was not configured, and the local machine had neither a usable B200 nor local Nsight traces. The run therefore inferred bottlenecks from end-to-end and per-shape timing rather than measuring occupancy, tensor-core utilization, HBM traffic, or launch gaps. The most useful next diagnostic is a caller-stream timeline plus per-kernel occupancy/memory counters for batch-64 n=256, batch-60 n=1024, batch-8 n=2048, and single-batch n=8192; those four cells represent every custom regime and would show whether the next work belongs in scheduling, movement, or math.

An unrepresented algorithm family behind the public leader. At the cutoff, the latest public leader was 178.772 µs versus this run’s last submitted 1006.765 µs, a 5.63× gap. Setup reuse and copy kernels cannot plausibly close a gap of that size by themselves. The next search should treat the leader as evidence that at least one substantially different factorization, fusion strategy, or benchmark-wide dispatch family remains absent, rather than continuing only sub-percent tuning of the current portfolio.

Shallow shape-specific fronts. Tensor-core decomposition for n=128, multi-CTA factorization for n=4096, and batch-aware triangular scheduling at n=1024 received only a few trials before the cutoff. These should be explored as dedicated shape objectives with explicit baselines and bounded tile/cluster/panel sweeps. In particular, n=128 sits between a synchronization-heavy shared-memory kernel and tensor-core-friendly dimensions, while batch-60 n=1024 has enough parallelism to justify alternatives to its serial four-panel dependency chain.

Low-batch multi-CTA large-matrix Cholesky. The run never produced a robust persistent multi-CTA implementation for batch-1/2 n=4096 and above. Direct cuSOLVER remained best at n=4096, and the custom CuTe route begins only at n=8192. A legal cooperative panel/update pipeline that overlaps independent trailing tiles on the caller stream could address the remaining sequential panel latency, but it needs cross-CTA synchronization and numerical safeguards that the one-CTA MathDx experiments did not exercise.

Cross-run and cross-GPU reproducibility. All prevalence and speedup evidence comes from one five-worker tree on one B200 benchmark, with a measured 1.765% coefficient of variation. Repeating the top family-level changes from the same baseline under new seeds, and then on another compatible GPU, would distinguish robust mechanisms from branch-parent effects, B200-specific scheduling choices, and noise-sized wins such as prewarming.
