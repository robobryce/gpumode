## Notes

- **Speedup** is local geomean vs the shared `main` baseline. Opus's best (`304e5f61f`) is also leaderboard-verified at 25,470 µs public, rank #4/58. Sol's current best commit (`866877a6`) is not yet submitted. (The Opus optimization report's "1.49× / 32,182 µs" is a mid-run snapshot of an earlier commit, not the run's final best.) Opus is finished at 2.21×; Sol is still running and at 2.06× has nearly closed the gap — a final Sol number will likely land higher.
- **Efficiency rows are a geometric per-unit-cost rate: `metric = speedup ^ (1 / cost)`** (cost in billion tokens or 1k code lines). This is a CAGR-style "by what factor did performance multiply per unit of cost." It is chosen so the zero-cost baseline (speedup 1.0, 0 tokens/lines) scores exactly 1.0 and any real gain scores > 1 — properties the earlier `speedup ÷ cost` and `(speedup − 1) ÷ cost` forms both failed (both diverge as cost → 0, so neither hits 1.0 at the baseline). Higher = more speedup per unit cost. The two rows split: Opus is more token-efficient (1.108 vs 1.071 per B tokens), Sol slightly more code-efficient (1.187 vs 1.176 per 1k lines).
- **Tokens** are summed from harness session logs with the same definition on both sides: total processed = all input (incl. cache reads) + output. Cache reads dominate both. The token *ratio* is method-consistent; the Sol absolute is a slight upper bound (a cross-check against a published autocuda cost report for a different finished Codex-harness run ran ~35% high, because this method counts resumed-session context re-reads).
- **Errors** = log rows with status validation_error / runtime_error / build_error. The gap (1.7% vs 17.8%) largely reflects that Opus resumed onto a mature, already-debugged kernel lineage and spent trials tuning/combining, whereas Sol authors kernels from scratch.
- **NCU / NSYS profiler calls** = tool calls (Claude Code `Bash`; Codex `exec`) whose command invokes the harness profiling wrappers `harness/profile_ncu.sh` / `harness/profile_nsys.sh` (or the raw `ncu` / `nsys` binary as a segment-leading command with a real subcommand/flag). The eigh harness mandates profiling through those wrappers, so counting bare binary names alone misses ~99% of them. Prose mentions of "ncu"/"nsys" in commit messages and log `--description` text are excluded by anchoring on the command boundary. Both runs use `nsys` (cheap per-kernel summary) far more than `ncu` (expensive full-section replay), per the harness's own guidance; Opus profiles more per trial (0.63 nsys, 0.15 ncu vs Sol's 0.50, 0.04).
- **Best submission is custom-kernel on both sides** (not pure PyTorch/cuSOLVER orchestration): Opus = 12 `__global__` CUDA kernels (mega_eigh family, warp/mw Jacobi, fused Gram-Cholesky) + Triton (4 `@triton`, 57 `tl.*`) + cuSOLVER floor; Sol = 23 `__global__` kernels (blocked Householder band→tridiag pipeline + certificate), no Triton.
- **Tree metrics** are `autocuda status` diversity (Shao & Sokal B2 balance index). The combined-Opus tree was reconstructed as one logical search tree (run1 rooted at `main`, run2 grafted onto run1's `d6553505f` trial node) and scored with the shipped algorithm; the method was validated by reproducing run2-alone's official numbers exactly. Opus stays far more exploratory (11.72 effective directions across 119 leaves) than Sol (5.53 across 31 leaves) despite comparable node counts — Sol concentrates on fewer lineages.
