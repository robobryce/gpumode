# GPUMODE QR — Skill Audit

## Executive Summary

I found **six confirmed autocuda skill/CLI issues (2 high, 3 medium, 1 low)** plus a coverage gap spanning the whole pre-built data CSV. Both high-severity bugs defeat core deliverables: **`report data optimization` blanks both speedup columns on 100% of optimize-tree rows** (it resolves the metric name from a shared schema file that now holds eigh's metric), and the **optimize-tree manager issued a "revert-if-it-doesn't-win" directive that contradicts explore-brief's "commit what you measured" rule**.

Key takeaways:

- **High — tree-run speedups are unrecoverable from the tool** — 0/5,602 rows carry a speedup, forcing manual recovery from raw logs.
- **High — the manager revert directive discarded measured regressions** the branch existed to capture; self-corrected mid-run.
- **Medium — `schema check` crashes on large fields** — 315 oversized `branches` cells trip Python's 128 KB cap, wrongly gating a valid report.
- **The pre-built skill CSV is 100% coverage-gap rows** — built without `--harness-jsonl`; findings come from a direct-JSONL scan.
- **The raw detector is ~87% false positives** — and the one genuine operator-facing gate was correct behavior, not a bug.

## Root Causes

**Contradictory instruction — optimize-tree manager vs. explore-brief worker (the one high-severity finding).** In `2026-06-25-22-03-01-qr_v2` (manager session `ad61ef45-4766-4ffe-b847-6fc766eb426d.jsonl`) the manager broadcast a "MANDATORY MANAGER DIRECTIVE" to all three workers (lines 1179/1181/1183, ts ~2026-06-26T07:49Z): *"It does NOT win → REVERT it ENTIRELY (git revert / restore to the clean parent). Do not leave it gated-off in the tree."* This directly contradicts explore-brief/SKILL.md §"Commit what you measured": *"Commit the live code you actually ran, with its real metric — even a regression… don't return a brief reverted to its parent: that discards the measured result the branch exists to capture."* The manager later admitted the error verbatim (line 1226, ts 07:54:02Z): *"I've now read the actual worker skill (explore-brief)… I had it backwards,"* and re-sent corrected instructions (lines 1235+). The root cause is an **authoring gap in optimize-tree/SKILL.md**: the manager skill never states that workers commit every measured trial (regressions included) and that the manager must not order reverts. The manager operated on an assumed model of the worker skill it had never read. This recurred and was self-corrected within the run, but it cost real trials (workers had "banked OFF" and reverted-to-parent commits, discarding measurements). This is version-independent and still latent in 0.4.0.

**Report markdown/CSV schema-contract mismatch — the schema-check field limit.** `_schema_check.py:_check_csv_body` opens the CSV with a bare `csv.reader(f)` and iterates rows (line 62) without ever calling `csv.field_size_limit()`. Python's default 128 KB per-field cap raises `_csv.Error` on any cell above it, and the exception is uncaught, so `autocuda schema check report-optimization-csv` exits 1 with a traceback rather than a schema verdict. The consolidated optimization CSV has 315 `branches` cells over that cap (the aggregation concatenates every contributing branch name for a technique). Because report-optimization/SKILL.md step 2 says *"If it fails, do not ship the report — fix the data step first,"* this tooling crash would incorrectly gate a valid, large, multi-run report. The file to patch is `_schema_check.py` (raise the limit before reading); optionally the data builder in `_report.py` should cap or `repr`-truncate the `branches` cell.

**Metric→speedup join failure — `report data optimization` blanks both speedup columns on every optimize-tree run (the second high-severity finding).** The report-optimization SKILL's whole point is to rank techniques by `best_step_speedup` (marginal) and headline by `best_speedup` (end-to-end), and SKILL step 3 tells the agent to cluster and rank on those columns. But `autocuda report data optimization` emits both columns blank for 100% of optimize-tree rows: 0/5,602 in the consolidated CSV (including all 1,436 qr_py rows), and I reproduced 0/676 for `2026-06-22-09-10-03-qr_v2` and 0/206 for `2026-06-29-06-40-42-qr_v2` by re-running the CLI. The data is NOT missing — the raw brief/worker logs carry real microsecond values in the `linalg/qr_v2` metric column (400 numeric rows, 394 on `succeeded` status, for the 06-22 tag). I traced the exact break in `_report.py`: `cmd_report_build_optimization` (lines 538–539) sets `metric_name = _primary_benchmark(experiments)["name"]`, and `_primary_benchmark` (line 443) loads the **single shared `autocuda/log-schema-optimize.json`**. In this data dir that file currently describes the concurrent **eigh** run (`{"name": "linalg/eigh_py"}`), not qr_v2. Every speedup computation then guards on `metric_name in r["metrics"]` (e.g. `_baseline_value` line 487, `_metric_by_sha` line 515), and the qr_v2 trial rows carry `{"linalg/qr_v2": …}`, so the key never matches → baseline resolves to `None`, `metric_by_sha` is empty, and every `best_speedup`/`best_step_speedup` is left blank. I proved the mechanism by forcing `metric_name="linalg/qr_v2"`: the baseline immediately resolved (1639.17 µs) and per-trial speedups computed correctly (0.946 / 1.001 / 1.008× on brief-6). So the primary, live root cause is that the aggregator resolves the benchmark **name** from a process-global schema file rather than from the run being reported — which also means a consolidated multi-run report inherits whichever single schema last landed in the data dir. A **secondary, historical contributor** compounds it on the older tags: their branch leaves are `worker-N-brief-K` and their logs are `<tag>-optimize-tree-worker-N-log.csv`, but the current 0.4.0 `_LEAF_BRIEF_PATTERN` is `^brief-(\d+)$` and `_branch_log_paths` globs `…-optimize-tree-brief-<K>-log.csv`, so those branches resolve to no brief-log at all. The reference-log's presence did NOT fix the 06-29 case (it uses the current naming and still gave 0/206), which confirms the schema-name join is the primary bug, independent of the missing-reference-log and naming-skew factors. Net effect: report-optimization is unusable as written on its primary target (tree runs) — the optimization-report agent had to recover every speedup by hand from raw logs and git commit messages.

**Missing setup / uncaught subprocess error — `init brief` on a dirty worktree.** `_init.py` `cmd_init_brief` (line 398, `else` branch) runs `subprocess.run(["git","checkout","-b",branch,primary_parent], check=True)`. When the brief worktree has uncommitted changes (a duplicate worker instance, or a resume after a crash left edits), git aborts with "Please commit your changes or stash them before you switch branches" and `check=True` raises `CalledProcessError`, which propagates to `autocuda_cli.py:2404` (`sys.exit(main())` in live 0.4.0; the recorded traceback shows the older CLI's line) as a raw traceback handed to the worker. Observed 20 distinct times across 6 tags — 13 in qr_py (autocuda **0.3.0**, `_init.py:401`) and the rest in qr_v2 0.4.0 (`_init.py:421` frame). Workers recovered by manually cleaning the worktree (e.g. `2026-06-19-04-54-07-qr_v2`: "There are leftover uncommitted changes… Let me find my worktree and clean it up"), so it was non-fatal but burned context and is poor UX. The fix is defensive handling in `cmd_init_brief` plus a recovery note in explore-brief/SKILL.md.

**CLI version skew across the run history (largest by raw volume, mostly benign).** 733 distinct CLI-arg rejections show the runs were executed on an **older autocuda than the installed 0.4.0**. The evidence: usage strings in the records list `--agent-id AGENT_ID` as REQUIRED for `autocuda run slice` and present on `autocuda log optimize-tree brief`; the live 0.4.0 `autocuda run slice/exclusive --help` has no `--agent-id`, and `log optimize-tree brief --help` uses `--tag/--parent-commit/--brief-kind/--description` with no `--agent-id`. Likewise the records show an `iteration` log verb and `brief_stop`/`brief-stop` status tokens, while 0.4.0 uses `trial` and rejects those. The current 0.4.0 SKILL.md prose is self-consistent with the current CLI (optimize-tree/explore-brief/discover all state "No `--agent-id`"; explore-brief uses `optimize-tree trial`). So these are **already-fixed historical mismatches**, not live skill bugs — but they are indistinguishable from a live break in the report unless the CLI version is captured. The remaining "invalid choice" rejections (`valid`, `success`, `keeper`, `show`) are agents guessing enum tokens, not skill-doc errors.

**Layout schema-contract at discovery time (isolated).** One kernel-language run (`t5sr96or9`) generated a `layout.md` that failed `autocuda schema check layout` on all nine required sections (the six in the table Evidence — Summary, Editable files, Read-only files, Build, Validation, Benchmarks — plus `## Cross-benchmark aggregation`, `## Dependencies`, and `## Log schema`). discover/SKILL.md line 92 documents the correct heading set and order, so this is an authoring miss (the agent wrote the file without the enforced `## `-heading structure) rather than a template that contradicts the schema. It is low severity (one run, caught by the checker) but argues for making the schema-check a mandatory gate in the discover write-layout step.

## Fix Plan

1. **optimize-tree/SKILL.md — close the revert/commit contradiction (high).** Add to §"Methodology" and §"Operating rules": *"Workers commit every measured trial, including regressions (see explore-brief §'Commit what you measured'). Never instruct a worker to revert, gate-off, or restore-to-parent a change it measured — that discards the result the branch exists to capture. The manager selects parents; it does not order reverts."* Validation: grep optimize-tree/SKILL.md for "revert" and confirm it forbids manager-ordered reverts; confirm the statement matches explore-brief/SKILL.md §"Commit what you measured".

2. **`_report.py` `report data optimization` — join the metric so tree speedups populate (high).** In `cmd_report_build_optimization`, stop resolving the benchmark name from the process-global `log-schema-optimize.json`: resolve it per-run (from the tag's own schema, or fall back to the metric column present in the run's brief/worker log rows) so `metric_name in r["metrics"]` matches. Also widen `_LEAF_BRIEF_PATTERN` (currently `^brief-(\d+)$`) and `_branch_log_paths` to accept `worker-N-brief-K` leaves and `…-optimize-tree-worker-N-log.csv` files so older-format tags resolve their brief-logs. Add a regression test on a tree-log fixture asserting non-blank `best_speedup`/`best_step_speedup`. Validation: `autocuda report data optimization --tag 2026-06-29-06-40-42-qr_v2 --output t` then assert >0 non-blank `best_speedup` in `t-report-optimization.csv` (proven achievable: forcing the correct metric name yields 0.946/1.001/1.008× on brief-6).

3. **`_schema_check.py` — stop crashing on large fields (medium).** At module load or the top of `_check_csv_body`, add `csv.field_size_limit(sys.maxsize)` (mirroring how any consumer must read these CSVs). Optionally, in `_report.py` cap the aggregated `branches` cell (store a count + first-N SHAs, or `repr`-truncate at ~100 KB). Validation: `autocuda schema check report-optimization-csv --output 2026-06-13-to-2026-06-29-qr-consolidated` must exit 0 (or report genuine field/row errors) instead of raising `_csv.Error`.

4. **`_init.py cmd_init_brief` — handle a dirty checkout (medium).** Wrap the `git checkout -b` (0.4.0 `_init.py:398`) in a `try/except subprocess.CalledProcessError`; on the "would be overwritten" abort, either `git stash`/`git reset --hard <parent>` the brief worktree (it is a scratch worktree) or print a single actionable line ("brief worktree has uncommitted changes; reset it to <sha> and re-run"). Add a short recovery note to explore-brief/SKILL.md §Setup for `MODE="resume"`. Validation: run `autocuda init brief` in a worktree with a dirty tracked file and confirm no Python traceback reaches the caller.

5. **export/SKILL.md + report-skill/SKILL.md — record and surface CLI version (medium).** Have `autocuda export` stamp the autocuda CLI version into the export branch, and have report-skill note the run's CLI version so `--agent-id`/`iteration`-style rejections are labeled "historical version skew" vs. "live contract break." Validation: an export branch contains a version marker; a skill report over an old-version run flags version skew rather than a current bug.

6. **discover/SKILL.md — gate layout on the schema (low).** Add a step after writing `layout.md`: *"Run `autocuda schema check layout` and fix any missing/out-of-order section before proceeding."* Validation: `autocuda schema check layout` exits 0 on the generated `layout.md` before the optimize loop starts.

7. **report-skill/SKILL.md / `report data skill` — default to discovering harness-records (info/coverage).** The CLI already documents auto-searching `<data-dir>/harness-records/`, `.claude/projects/`, `.codex/sessions/` when no `--harness-jsonl` is passed, but the pre-built consolidated CSV shows it emitted only `missing_harness` rows — i.e. the auto-discovery either wasn't triggered (paths outside the data dir) or found nothing. Fix: either always pass `--harness-jsonl` for consolidated runs, or make `report data skill` warn loudly when 100% of rows are `missing_harness`. Validation: re-running with the `/tmp/qrwork/harness/**` mappings yields non-coverage rows.

## Scope & Methodology

Consolidated audit for bugs in the **autocuda skills themselves** across all
qr_py + qr_v2 experiments: 18 qr_v2 main-lineage tags (B200), 22 qr_v2
kernel_languages tags (RTX Pro 6K), and 1 qr_py tag (B200, `2026-06-13-03-45-35`,
1,161 kept trials) plus its stashes — 41 optimize tags, 3,089 experiment branches,
6,450 session JSONLs (~4.2 GB). Kernel build/validation/optimization failures are
**out of scope** and are treated as run outcomes, not skill bugs.
